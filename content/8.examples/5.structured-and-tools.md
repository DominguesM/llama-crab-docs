These examples show two related patterns: constraining the model to
JSON, and turning model output into a Rust-side function call.

## Structured JSON

```bash [Terminal]
./run.sh structured
```

The example:

1. Defines a JSON Schema with `name` and `age`.
2. Converts it with `json_schema::schema_to_grammar`.
3. Creates a grammar sampler with `LlamaSampler::grammar(...)` (this
   call returns `Result<LlamaSampler, GrammarError>` and must be
   wrapped in `unsafe { ... }` because it dereferences raw FFI
   pointers).
4. Chains the grammar sampler with greedy decoding through
   `LlamaSampler::chain(vec![...], false)`.
5. Parses the final text with `serde_json`.

This is the right pattern when the response itself must conform to a
schema. The `common` cargo feature must be enabled for the grammar
sampler to link.

## Tool call demo

```bash [Terminal]
./run.sh tools
./run.sh tool_calls_qwen
```

The current tool example keeps the runtime simple:

1. The system message tells the model to return one JSON call.
2. Rust extracts and validates the JSON.
3. Rust executes a local `get_weather` fixture.
4. The example prints both the tool call and tool result.

The high-level chat API supports five tool-call wire formats
(`ToolFormat`):

- `ChatMl` (Qwen, OpenHermes, …)
- `Mistral`
- `Llama3` (Llama 3 / Llama 3.1)
- `Plain` (raw JSON)
- `Functionary` (v1 / v2)

The `ToolParser` non-streaming parser and `ToolCallStream` OpenAI-style
streaming deltas are both available; the streaming path emits
`id`/`name`/`arguments`/`completed` chunks that mirror the OpenAI wire
format. See [Rust SDK: Chat](/rust/chat) for the full tool-call API.

Use this pattern when the model should select or populate an action but
your application owns execution, authorization, and error handling.

## Server support

The HTTP server accepts structured response hints and tool definitions
on `/v1/chat/completions`. The structured-output priority chain is
`grammar` → `json_schema` → `response_format` → `grammar_root`. The
`response_format.type` values the server accepts are `text`,
`json_object`, and `json_schema`; any other value fails with
`unsupported response_format type`. For production APIs, validate
model output server-side even when grammar or tool hints are present.
